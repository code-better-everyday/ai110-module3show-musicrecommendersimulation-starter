## Design Pattern (SF10)

> Document how AI helped you choose or implement a design pattern.

**Which design pattern did you use?**

Strategy Pattern — implemented via the `Recommender` class in `src/recommender.py`.

**How did AI help you brainstorm or implement it?**

When designing Phase 3, Claude Code proposed encapsulating the scoring algorithm inside a `Recommender` class rather than leaving it as a standalone function, so that the scoring strategy could be swapped or extended without changing the calling code in `main.py`. The reasoning was that the test suite (`tests/test_recommender.py`) needs an OOP interface (`Recommender.recommend()`, `Recommender.explain_recommendation()`) while the production runner (`main.py`) can use the lighter functional API (`recommend_songs()`). Both interfaces call the same underlying `score_song()` function, making the strategy a single pluggable unit rather than scattered logic.

The design was validated when Phase 6 added a `format_score_table()` helper and `apply_diversity_filter()` in `main.py` — because all scoring logic lives inside `score_song()` in `recommender.py`, the new display and diversity features were added entirely in `main.py` without touching the algorithm at all. That separation is the Strategy pattern working as intended.

**How does the pattern appear in your final code?**

- [`src/recommender.py:33`](src/recommender.py) — `class Recommender` is the Strategy container
- `Recommender.recommend(user, k)` — applies the scoring strategy against a `UserProfile` and returns ranked `Song` objects
- `Recommender.explain_recommendation(user, song)` — applies the same strategy to a single song and returns a human-readable explanation string
- `score_song(user_prefs, song)` — the core algorithm, isolated and independently unit-testable without instantiating the class
- `main.py` is fully decoupled from the algorithm: it calls `recommend_songs()` (the functional wrapper) and never touches scoring weights or rules directly
